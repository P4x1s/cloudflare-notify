# Cloudflare Notify 产品改进路线图

> 基于 **v1.9.2 实际源码**（`worker.js`，单文件 ~3100 行）审计得出。本文只做产品与改造评估，不涉及代码实现。
> 审计时间：2026-11-27
>
> **实施状态（2026-11-27 更新）**：路线图全部条目已在 **v2.1.0** 落地。v2.0.0 完成 U1/U2/U3/U5/U6、C1～C6、E1～E6 与 L2；v2.1.0 补齐 U4（语法高亮/行号/折叠/密钥脱敏）、E7（品牌化登录页）与 L1/L3/L4/L5/L6（导出、双语、统计、API 文档、多租户准备）。**v2.2.0** 在此之上补强主密钥保存、三渠道测试入口，并完成一轮安全加固（管理凭据禁止走 URL、飞书 Webhook 路径脱敏、渠道测试限流/签名/审计）。完整变更见 [V20_RELEASE.md](V20_RELEASE.md)、[V21_RELEASE.md](V21_RELEASE.md) 与 [V22_RELEASE.md](V22_RELEASE.md)。

---

## 0. 结论速览

项目当前是一个**功能扎实但偏个人工具**的通知中心：接收端灵活、企微推送稳定、界面整洁，但在「多渠道、可管理、可运维」三个维度上还有明显差距，距离商业化产品还差 3～5 个关键能力。

| 阶段 | 核心目标 | 预期成果 |
|---|---|---|
| **近期必做（1～2 个月）** | 补上多渠道抽象与消息管理基础 | 可接钉钉/飞书、消息可搜索/删除/分页、界面移动端可用 |
| **中期优化（3～6 个月）** | 提升可运维性与专业感 | 模板系统、发送状态追踪、渠道健康看板、限流保护 |
| **长期布局（6 个月+）** | 支撑商业化与规模化 | 多租户准备、开放 API 生态、付费功能分层 |

## 第一部分：通知渠道扩展

### 现状问题

1. **渠道硬编码**：`pushToWecom(env, message)` 是唯一出站通道，Webhook URL 来自 `env.WECOM_WEBHOOK` 单个 Secret。新增渠道意味着改核心函数。
2. **无渠道抽象层**：`createMessage()` 和 `serverchanSend()` 都直接 `await pushToWecom()`，没有统一的渠道接口定义。
3. **无渠道配置管理**：每个渠道的 Webhook、密钥、开关都散落在环境变量里，没有面板配置入口。
4. **无发送状态追踪**：`recordDelivery()` 只记企微单渠道的投递结果，无法知道「这条消息推给了哪些渠道、各自的成败」。
5. **无重试策略**：企微单次尝试即放弃；不同渠道的限流/重试策略不同（钉钉每分钟 20 条、飞书每小时 500 条），需要差异化处理。

---

### 建议改动

#### C1｜建立统一渠道抽象层（P0）

**改动内容**：
- 定义渠道接口：`{ id, name, send(message) → { ok, error, latency }, test(), isConfigured() }`
- 将 `pushToWecom` 改造为 `WecomChannel` 实现该接口的第一个实例
- `createMessage()` 改为遍历已启用的渠道列表，并行发送（`Promise.allSettled`），各自记录结果
- 保留既有返回结构 `wecom: { configured, ok, error }` 向后兼容，新增 `channels: [{ id, name, ok, error }]`

**用户价值**：后续加渠道不再动核心流程；调用方一眼看出每个渠道的送达情况。

**优先级**：P0（所有后续渠道扩展的前置条件）

**大致工作量**：2～3 天（含重构测试）

---

#### C2｜补充钉钉群机器人渠道（P1）

**改动内容**：
- 新增 `DINGTALK_WEBHOOK` Secret，支持钉钉自定义机器人 Webhook
- 实现 `DingtalkChannel`：钉钉用 `msgtype: "markdown"` 或 `text`，标题字段为 `title`（markdown 类型必需）
- 支持钉钉签名校验（如果对方开启了加签安全设置）—— inbound 暂不需要，outbound 是我们推给钉钉，不需要签名
- 面板增加钉钉配置区：Webhook 输入框 + 「测试发送」按钮 + 启用开关
- 接入面板增加「钉钉」示例标签

**注意**：钉钉 markdown 语法与企业微信不完全兼容（不支持 `>` 引用块、表格支持有限），需要做降级转换。

**用户价值**：覆盖大量使用钉钉的中小企业和国内开发者群体。

**优先级**：P1（国内第二大办公 IM，覆盖面仅次于企微）

**大致工作量**：3～4 天（含语法转换适配、面板配置、测试）

---

#### C3｜补充飞书群机器人渠道（P1）

**改动内容**：
- 新增 `FEISHU_WEBHOOK` Secret，支持飞书自定义机器人 Webhook
- 实现 `FeishuChannel`：飞书 payload 格式为 `{ msg_type: "interactive", card: {...} }` 或 `text`
- 飞书支持富文本卡片（post）、模板卡片，视觉效果比企微更好，值得做卡片格式
- 面板增加飞书配置区 + 接入示例

**注意**：飞书 Webhook 不支持签名（自建应用 Webhook 才支持），安全性略低于企微的加签选项。

**用户价值**：飞书在互联网、创业团队中普及率高，卡片消息视觉效果好。

**优先级**：P1（与钉钉并列，可并行开发）

**大致工作量**：4～5 天（飞书卡片 schema 较复杂，交互式卡片需要更多适配）

---

#### C4｜多渠道统一配置面板（P1）

**改动内容**：
- 侧边栏新增「渠道管理」section（或并入现有「测试通知」模块）
- 每个渠道一张小卡片：名称、状态徽标（已配置/未配置）、Webhook 输入框（password 类型）、测试按钮、启用开关
- 配置持久化到 KV（`meta:channels`），而非只依赖环境变量——让用户能在面板里改配置，不用碰 Cloudflare Dashboard
- 敏感字段（Webhook URL）加密存储或至少 password 输入

**用户价值**：降低配置门槛，用户不用登 Cloudflare 后台就能切换/测试渠道。

**优先级**：P1（与 C2/C3 配合推出，否则面板加了渠道也没法配置）

**大致工作量**：3～4 天（含 KV 配置存储、面板 UI、迁移逻辑）

---

#### C5｜通知模板系统（P2）

**改动内容**：
- 支持命名模板：用户在面板保存「构建失败」「上线成功」等模板（标题模板 + 内容模板 + 适用渠道）
- 发送时可指定 `template=xxx` 参数，服务端合并变量渲染
- 模板存 KV，支持增删改查 API

**用户价值**：不同业务场景用不同格式，不用每次都拼 HTML/变量。

**优先级**：P2

**大致工作量**：3～4 天

---

#### C6｜发送状态与投递明细（P2）

**改动内容**：
- 每条消息记录 `deliveries: [{ channel, ok, error, latency, at }]` 存 KV
- 消息详情页/展开区显示各渠道送达状态图标（✓/✗/⏳）
- `/api/status` 增加渠道级指标：各渠道最近成功时间、连续失败数、今日发送量

**用户价值**：出问题能定位是哪个渠道挂了，不用挨个查。

**优先级**：P2（C1 完成后才有数据结构支撑）

**大致工作量**：2～3 天

## 第二部分：界面与交互改进

### 现状问题

1. **移动端只有断点，没有适配**：980px 以下侧边栏折叠到上方，但表单元素、代码框、按钮行在小屏上仍拥挤；没有针对 < 600px 的专门优化。
2. **无导航结构**：所有内容在一个长页面里，通知列表和工具模块混排，消息多时要滚很远才能到工具区。
3. **消息列表缺少管理能力**：只能「全部清空」，没有单条删除、搜索、按来源过滤、按时间排序切换。
4. **无深色模式手动切换**：跟随系统，用户无法手动覆盖。
5. **代码框体验一般**：字体小、无语法高亮、无行号、长内容只能滚动。
6. **Toast 反馈太短暂**：成功/失败提示几秒就消失，复杂操作（如轮换密钥）后用户可能没看清。
7. **无障碍不足**：部分交互缺少 ARIA 标签，键盘导航覆盖不全。
8. **登录页无品牌感**：只有一个输入框，与主界面风格割裂。

---

### 建议改动

#### U1｜移动端深度适配（P0）

**现状**：只有一个 `@media (max-width: 980px)` 断点，侧边栏上移但内部元素未优化。

**改动内容**：
- 新增 < 600px 断点：侧边栏 section 改为可折叠的 accordion（默认只展开当前使用模块）
- 按钮行改为全宽 stacked 布局，主要按钮在上、次要按钮在下
- 代码框高度自适应（最大 200px），字体增大到 12px
- 消息卡片内边距缩小到 10px，标题字号缩小到 13px
- 底部固定操作栏（展开/折叠/刷新）在小屏上吸底
- 输入框 `font-size: 16px` 防止 iOS 聚焦时缩放

**用户价值**：手机上能正常收发通知、管理密钥，这是「随时查看告警」的核心场景。

**优先级**：P0（移动端是不可忽视的通知使用场景）

**大致工作量**：2～3 天

---

#### U2｜消息列表管理能力（P0）

**现状**：只有「全部展开/折叠」「刷新」「全部清空」，无单条操作、无搜索、无过滤。

**改动内容**：
- 每条消息 hover/长按时显示操作按钮：删除、复制内容、重新推送（调用 `/api/send` 重发该消息）
- 顶部搜索框：按标题/内容/来源模糊匹配，实时过滤（前端过滤，无需后端改动）
- 来源过滤 chips：全部 / github-actions / prometheus / cron / routerhook / system
- 时间分组：今天 / 昨天 / 更早，折叠显示

**用户价值**：通知多了之后能找到关键信息、清理垃圾消息，这是通知中心从「Demo」走向「工具」的标志。

**优先级**：P0

**大致工作量**：3～4 天（删除需后端 API，搜索/过滤/分组可纯前端实现）

---

#### U3｜导航结构调整（P1）

**现状**：通知列表和三个工具模块在一个长页面，无锚点导航。

**改动内容**：
- 左侧栏（桌面端）增加迷你导航：📥 通知 / 📤 接入 / 🔑 密钥 / ✉️ 发送，点击平滑滚动到对应区域
- 移动端折叠为顶部下拉或底部 Tab Bar（3～4 个核心入口）
- 滚动时高亮当前所在区域

**用户价值**：减少滚动寻找成本，界面更像一个「应用」而非「文档页」。

**优先级**：P1

**大致工作量**：2～3 天

---

#### U4｜代码块与示例体验（P1）

**改动内容**：
- 代码框增加简单的语法着色（关键字/字符串/注释三种颜色，纯正则实现，不引依赖）
- 增加「一键复制」按钮悬浮在代码框右上角（不只是卡片头的复制按钮）
- 代码过长时折叠，显示前 N 行 + 「展开」按钮
- 示例代码中的密钥部分自动脱敏显示（`x********x`），复制时才给完整值

**用户价值**：接入示例是用户最常看的页面，体验直接影响转化率和客服咨询量。

**优先级**：P1

**大致工作量**：2 天

---

#### U5｜深色模式手动切换（P2）

**改动内容**：
- 页头增加 🌙/☀️ 切换按钮，三态：跟随系统 / 浅色 / 深色
- 偏好存 localStorage，下次访问记住
- 切换时无闪烁（在 `<head>` 内联脚本提前设置）

**用户价值**：部分用户夜间查看告警，深色模式更舒适。

**优先级**：P2

**大致工作量**：1～2 天

---

#### U6｜配置自检可视化升级（P2）

**现状**：自检是一条横向 banner，正常时隐藏，异常时显示。

**改动内容**：
- 改为常驻的「服务状态」小组件（页头或侧边栏底部），显示 5 个核心依赖的健康状态图标
- 异常时红色徽标 + 点击展开详情与修复指引
- 增加「上次检查时间」和「自动刷新」选项

**用户价值**：用户不用等到发不出消息才发现配置问题。

**优先级**：P2

**大致工作量**：1～2 天

## 第三部分：核心体验改进

### 现状问题

1. **无单条消息删除**：只有「全部清空」（需管理密钥 + 二次确认），误发了垃圾消息只能全删。
2. **无消息搜索**：通知多了之后无法回溯历史告警。
3. **无发送速率限制**：`/api/send` 和 `/<key>.send` 无限流，免费 KV 只有 1000 写/天，可被恶意刷爆。
4. **无幂等去重**：上游重试（如 CI 重跑、监控重报）会产生重复消息 + 重复企微推送。
5. **无静默时段**：深夜也会推企微，没有「免打扰」能力。
6. **无消息统计**：不知道每天收到多少条、哪个来源最多、失败率多少。
7. **登录页无品牌**：纯白底单输入框，与主界面风格不一致，也没有项目说明。
8. **无健康检查端点之外的运行监控**：Cloudflare Analytics 能看请求量，但看不到「消息成功率」「渠道延迟」等业务指标。
9. **变量模板仅服务端渲染**：发送前无法预览替换后的结果，写错变量名只能发出去才知道。
10. **清空操作无确认弹窗样式**：用的是 `confirm()` 浏览器原生弹窗，风格不统一。

---

### 建议改动

#### E1｜单条消息删除与批量操作（P0）

**改动内容**：
- 新增 `DELETE /api/messages/:id`（管理密钥鉴权）
- 消息卡片增加删除按钮（hover 显示），点击后行内确认（不用原生 confirm）
- 支持勾选多条批量删除
- 删除前写操作日志（`meta:audit`），满足商用客户的审计需求

**用户价值**：日常使用的基本操作，没有就会显得「不完整」。

**优先级**：P0

**大致工作量**：2 天（后端 API + 前端交互 + 确认流程）

---

#### E2｜发送入口限流（P0）

**现状**：除登录接口外，所有发送入口无限流。免费 KV 写入额度 1000 次/天，恶意请求半天就能打满。

**改动内容**：
- 基于 IP + 密钥双维度限流：单 IP 每分钟 30 次、每天 200 次；单密钥每分钟 60 次、每天 500 次
- 用 Cloudflare 自带的 Rate Limiting 规则（免费版每月 10 条规则）或 Worker 内内存计数器（单 isolate 不精确但够用，生产建议配合 CF Rules）
- 超出限额返回 429 + `Retry-After` 头，错误信息明确告知「请求过于频繁」

**用户价值**：保护免费额度和服务稳定性，避免被刷爆后正常用户也用不了。

**优先级**：P0

**大致工作量**：1～2 天

---

#### E3｜幂等去重（P1）

**改动内容**：
- 支持 `X-Idempotency-Key` Header 或 `&idempotency_key=` 参数
- 服务端用 `meta:idem:<key>` 存最近 24 小时的幂等记录（key + 首次响应）
- 相同 key 重复请求直接返回首次结果，不重复落库、不重复推送
- 对 RouterHook 场景特别有用（其本身就带重试机制）

**用户价值**：消除 CI 重跑、监控抖动导致的重复通知刷屏。

**优先级**：P1

**大致工作量**：2～3 天（注意 KV 写额度，幂等记录要设 TTL 自动过期）

---

#### E4｜变量模板预览（P1）

**现状**：发送前看不到 `{date}` `{time}` `{source}` 等变量替换后的效果。

**改动内容**：
- 发送测试模块增加「预览」按钮：点击后用当前时间 + 示例值实时渲染变量，显示在输入框下方
- 未知变量名高亮警告（如 `{dat}` 拼写错误）
- 面板接入示例中增加「预览变量」快捷入口

**用户价值**：降低变量模板的使用门槛，减少「为什么 {date} 没展开」的困惑。

**优先级**：P1

**大致工作量**：1～2 天（纯前端逻辑，复用现有 `renderVars` 函数）

---

#### E5｜静默时段 / 免打扰（P2）

**改动内容**：
- 面板新增「静默时段」设置：开始时间、结束时间、是否静默企微推送（网页收件箱仍记录）
- 配置存 KV，每次推送前判断当前时间是否在静默区间
- 静默时段内的消息标记 `silenced: true`，恢复后可选「补发摘要」

**用户价值**：夜间告警不扰民，适合个人用户和小团队。

**优先级**：P2

**大致工作量**：2 天

---

#### E6｜统一确认弹窗与操作反馈（P2）

**改动内容**：
- 替换所有原生 `confirm()` / `alert()` 为自定义模态框（与现有设计语言一致）
- 危险操作（清空、删除、轮换密钥）使用红色确认按钮 + 明确后果描述
- 操作反馈从 Toast 升级为：轻量操作用 Toast，重要操作（轮换成功、删除完成）用行内持久状态条

**用户价值**：界面专业度提升，减少误操作。

**优先级**：P2

**大致工作量**：1～2 天

---

#### E7｜登录页品牌化（P2）

**改动内容**：
- 登录页沿用主界面 CSS，增加项目 logo、一句简介、「回到首页」链接
- 未配置 READ_TOKEN 时显示「当前为公开模式，建议设置查看密钥」的温和提示
- 错误提示从页面顶部移到输入框下方，更直观

**用户价值**：客户部署后分享给团队成员时，登录页就是第一印象。

**优先级**：P2

**大致工作量**：1 天

## 第四阶段：长期布局（6 个月+）

| 编号 | 项目 | 说明 |
|---|---|---|
| L1 | **消息导出** | 支持 JSON / CSV / Markdown 导出，满足审计与迁移需求 |
| L2 | **Webhook 入站签名** | 可选开启 HMAC-SHA256 验签，让本项目也能作为可靠的接收方被第三方系统调用 |
| L3 | **多语言支持** | 中英文界面切换，面向海外用户 |
| L4 | **消息统计看板** | 每日/每周发送量、渠道分布、失败率趋势图 |
| L5 | **开放 API 文档页** | 服务端内嵌 Swagger/OpenAPI 文档，替代静态 README |
| L6 | **多租户架构准备** | 若做托管 SaaS，需先做租户隔离、配额管理、支付接入——这是独立的大工程，不建议现在开始 |

## 实施顺序总览

```
第 1～2 周：  U1 移动端适配 → E1 单条删除 → E2 限流
第 3～4 周：  U2 消息管理（搜索/过滤）→ C1 渠道抽象层
第 5～8 周：  C2 钉钉渠道 → C3 飞书渠道 → C4 多渠道配置面板
第 9～12 周：  E3 幂等去重 → E4 变量预览 → U3 导航重构
第 13～16 周： C5 模板系统 → E5 静默时段 → U4 代码块体验
第 17 周以后： L 系列长期项，根据商业化反馈决定优先级
```

**核心原则**：先让产品在「手机上好用、消息管得住、不会被刷爆」，再谈多渠道和商业化。前 4 周的 5 项工作（U1、E1、E2、U2、C1）能让项目从「个人玩具」变成「可交付给客户的工具」，这也是商业报价的基础。

## 第五部分：商业价值排序与 Cloudflare 免费额度测算

> 补充分析：2026-11-27。额度数据来自 Cloudflare 官方定价页（Workers / Workers KV / Durable Objects，DO 页更新于 2026-11-13）。
> 测算基于 v1.9.2 源码的实际 KV 调用链，不是理论估算。

### 5.1 哪些改动更有商业价值

按「客户是否愿意为它单独付钱」分成三层，而不是按技术难度排。

#### 第一层：定价杠杆（客户看得见、愿意单独付钱）

| 编号 | 改动 | 商业价值 | 能支撑的报价 |
|---|---|---|---|
| **C2 / C3** | 钉钉、飞书渠道 | 最直观的卖点：「一个后台同时推企微 + 钉钉 + 飞书」，客户一听就懂；覆盖面直接决定客单价 | ¥1999～3999 场景包的核心溢价来源 |
| **C4** | 多渠道统一配置面板 | 让客户的运维人员自己改 Webhook、不用登 Cloudflare 后台，是「可交付给团队」与「只能自己玩」的分界线 | 支撑 ¥999 → ¥1999 的套餐升级 |
| **C6** | 发送状态与投递明细 | 「出问题能定位是哪个渠道挂了」是售后承诺的依据；没有明细就不敢卖年度维护 | 年度维护费（实施费的 20%～30%/年）的交付凭证 |
| **E3** | 幂等去重 | RouterHook 自带重试、监控抖动会刷屏，这是真实痛点，能直接写进场景包的卖点文案 | 场景加价项，尤其适合 RouterHook 客户 |
| **L2** | 入站签名 + 审计记录 | 企业采购和合规常见要求，个人用户不会提，但企业客户会卡在这一条 | ¥5000+ 定制项目的门槛项 |
| **C1** | 渠道抽象层 | 本身不是卖点，是 C2/C3/C4 的前置投入；必须把成本摊进渠道包，不要单独拿它去报价 | 成本项，不是收入项 |

#### 第二层：成交前置（不加价，但不做就丢单）

| 编号 | 改动 | 为什么商业上仍然重要 |
|---|---|---|
| **U1** | 移动端深度适配 | 告警场景的核心动作就是「手机上看到并处理」；演示视频里手机端打不开，场景包很难成交 |
| **E1** | 单条消息删除 | 客户默认这是基本功能，缺失会被判定为半成品 |
| **U2** | 消息搜索/过滤 | 同上；通知一多就找不到历史告警，「工具感」的主要来源 |
| **E2** | 发送限流 | 不只是体验问题：它直接保护免费额度被打爆后服务不可用，是交付稳定性的基础 |
| **E5** | 静默时段 | 个人用户不敏感，但 RouterHook/NAS 客户对「深夜告警扰民」非常敏感，可提前做 |

#### 第三层：锦上添花（付费意愿低，后排）

U3 导航重构、U4 代码块体验、U5 深色模式、E4 变量预览、E7 登录页品牌化、C5 模板系统、L1 导出、L3 多语言、L5 开放 API 文档、L6 多租户。

这些能提升专业感和留存，但**在卖出 5 单之前不产生收入**。尤其 L6 多租户是独立大工程，必须在托管需求被真实验证后才启动。

#### 套餐与改动的映射

- **¥999 快速上线包**：U1 + E1 + E2 —— 交付底线，别指望靠它赚大钱。
- **¥1999～3999 场景集成包**：C1 + C2/C3 + C4 + E3 + E5 —— 主推，溢价全部来自「多渠道 + 不用碰后台 + 不刷屏」。
- **¥5000+ 定制项目**：L2 + 审计日志 + 多环境 + C6 + 明确响应时间的支持承诺。
- **年度维护**：以 C6 投递明细 + E2 限流为交付凭证，按实施费 20%～30% 报价。

### 5.2 Cloudflare 免费额度够不够用

#### 官方上限（每账号，每日 00:00 UTC 重置）

| 资源 | Workers 免费版 | 付费版（$5/月起） |
|---|---|---|
| Workers 请求 | 100,000 / 天 | 10,000,000 / 月，超额 $0.30/百万 |
| CPU 时间 | 10 ms / 次调用 | 30,000,000 CPU-ms / 月 |
| KV 读 | 100,000 / 天 | 10,000,000 / 月 |
| KV 写 | **1,000 / 天** | 1,000,000 / 月 |
| KV list / delete | 1,000 / 天 | 1,000,000 / 月 |
| KV 存储 | 1 GB | 1 GB + $0.50/GB-月 |
| Durable Objects（SQLite） | 100,000 请求/天；5,000,000 行读/天；100,000 行写/天；5 GB | 1,000,000 请求/月；超额另计 |

免费版的关键规则：**任一维度超额后，该类操作直接失败**，不是降速、也不是自动计费。

#### 按源码实测的消耗模型

每发一条消息（企微已配置）：

| 调用 | KV 操作 |
|---|---|
| `saveMessage()` | 2 次写（消息 key + `meta:version`） |
| `pushToWecom()` → `recordDelivery()` | 1 次读 + 1 次写（投递日志） |
| Server酱路径 `getCurrentSendKey()` | 1 次读 |
| **合计** | **≈ 3 写 + 2 读 / 条** |

面板每 5 秒轮询一次 `/api/messages?version=...`：

- 版本未变：1 次 Worker 请求 + **1 次 KV 读**；
- 版本变化：再加 1 次 `list` + 最多 50 次 `get`；
- 页面隐藏时暂停轮询。

#### 容量测算

| 场景 | 消息/天 | 浏览器标签 | KV 写 | KV 读 | KV list | 结论 |
|---|---:|---|---:|---:|---:|---|
| 个人自用 | 20 | 1 个 × 8 小时 | 60（6%） | ≈ 6,780（7%） | 20 | 非常宽裕 |
| 小团队 | 100 | 3 个 × 8 小时 | 300（30%） | ≈ 32,580（33%） | 300 | 够用 |
| 活跃团队 | 200 | 3 个 × 8 小时 | 600（60%） | ≈ 47,880（48%） | 600 | 可用，但写额度只剩 40% |
| **3 个客户共用你 1 个账号** | 300 | 9 个 × 8 小时 | **900（90%）** | **≈ 97,740（98%）** | 900 | 临界，随时失败 |
| 5 个客户共用 1 个账号 | 500 | 15 个 × 8 小时 | 1,500（超额） | > 100,000（超额） | > 1,000（超额） | 必然失败 |
| 单客户升级付费版 | 同上 | 同上 | 1,000,000/月 ≈ 33,000/天 | 10,000,000/月 ≈ 333,000/天 | 充足 | 余量约 100 倍 |

#### 三个必须记住的结论

1. **硬瓶颈是 KV 写 1000 次/天**：按 3 写/条算，理论上限约 333 条/天。建议对外标称 **≤ 200 条/天**，给密钥轮换（3 写）、清空消息、失败告警留余量。
2. **KV namespace 是账号级的，不是实例级的**：所有部署在同一个 Cloudflare 账号的实例共享同一份 1000 写/天。所以卖部署服务时，**必须让客户用他们自己的 Cloudflare 账号**——这也正好符合「数据自有」的卖点。只有每个客户独立账号，免费额度才真正够用。
3. **消息没有 TTL，会永久累积**：`saveMessage()` 的 `put` 没有 `expirationTtl`。按 20 KB/条 × 200 条/天 ≈ 4 MB/天计算，约 250 天就会触及 1 GB 上限。建议加「保留 N 天 / 最多 M 条」的清理策略，既是容量保护，也能作为合规卖点放进维护包。

#### 两个低成本优化（顺手做，直接省额度）

- **自适应轮询间隔**：把固定 5 秒改成「前台 5 秒 → 无变化 15 秒 → 长时间无变化 30 秒」，读请求可下降 3～6 倍；多标签页场景收益最大。
- **RouterHook 窗口**：默认 60 秒窗口意味着每台设备每天约 1440 次 alarm 请求，免费 DO 的 100,000 请求/天大约支持 69 台设备；超过约 50 台时把窗口调到 120 秒，或升级付费版。单台路由器场景完全没有压力。

#### 最终判断

**免费额度对「客户自带账号 + 单实例 + 每天 200 条以内」完全够用，可以放心卖 ¥999 / ¥1999 的部署与集成包。**

**免费额度对「你用一个账号托管多个客户」不够用**：3 个客户就到 98% 读额度、90% 写额度。所以商业模式应选「帮客户部署到他们自己的账号」（先卖服务），托管订阅要等付费账号 + 多租户隔离做完再做。若真要做托管，每个客户一个独立的 $5/月付费账号比强行多租户省事得多；按 ¥99/月收费，毛利约 ¥63/月/客户（未计支持成本）。
