# Webhook 接入方式梳理与演进建议

> 本文基于 **v1.9.0 实际源码**（`worker.js`）审计，不是通用科普。目的：分清「项目作为接收方」与「项目作为推送方」两个方向，逐项评估适用场景、可靠性、安全性、运维成本，并给出**哪些值得补进本项目**的明确结论与优先级。
>
> 涉及的安全建议均遵循业界通行做法（HMAC-SHA256 覆盖 raw body + 时间戳、常量时间比较、5 分钟容差、事件 ID 幂等等，参见 Stripe / GitHub / Slack 官方文档）。
>
> **落地状态（v1.9.1）**：本文的 **P0-a 失败告警** 与 **P0-b 投递可观测** 已实现并上线到代码——`pushToWecom()` 现在每次成功/失败都写一条脱敏投递记录（单 KV key 环形缓冲，上限 30 条），连续失败 3 次会自动向通知中心写系统告警消息（直接落库、不走推送，天然防环，10 分钟静默窗口）；`/api/status` 的 `diagnostics.delivery` 暴露 `lastAt / lastOkAt / lastError / consecutiveFailures / recentFailures / recent`。专项测试 `_test_delivery.mjs` 41 项通过。P1/P2 尚未实现，按下文优先级推进。

## 0. 结论速览（TL;DR）

当前项目的定位是「**极简通知中转站**」：接收端只要一个 key 就能投，推送端只连企业微信一个目标。这个取舍在个人/小团队场景是对的，但有 4 个**低成本、高收益**的缺口值得优先补：

| 优先级 | 要补的能力 | 为什么现在就该补 | 大致成本 |
| --- | --- | --- | --- |
| **P0** | 出站**失败告警**（推送企微失败时自通知） | 当前失败**完全静默**——调用方拿到 `wecom.ok:false` 也不看，消息看着"已接收"实际群里没收到 | 极低（几十行） |
| **P0** | 出站**投递记录 + 状态可观测**（最近成功/失败、重试次数） | 现在只能翻 Cloudflare 日志，且 `pushToWecom` 失败连 `console` 都没打 | 低（1 个 KV key 环形缓冲） |
| **P1** | 入站 **HMAC 签名校验**（可选开启，默认关） | 静态 key 一旦进 URL 就可能被日志/截图泄露；签名能证明"这条请求确实来自声明的发送方且未被篡改" | 中（Worker 里 raw body 天然可用，实现成本比传统服务低） |
| **P1** | 入站**事件 ID 幂等去重** | 任何走标准重试的上游都会重投；现在每次重投都重新落库 + 重新推企微 = 刷屏 | 中（注意免费 KV 写额度，见 §5.3） |

**明确不建议补**（至少现阶段）：mTLS、JWT/JWKS 非对称验签、独立重型队列 + DLQ、IP 白名单当主鉴权。理由见 §7。

## 1. 两个方向的定义（先把边界说清楚）

Webhook 有一种很容易混淆的双向性，本项目**两个方向都做**：

| 方向 | 含义 | 本项目具体端点/通道 | 我们扮演的角色 |
| --- | --- | --- | --- |
| **接收方**（inbound） | 别人把事件推给我们 | `GET/POST /send`、`POST /api/send`、`GET/POST /<key>.send`（兼容端点）、`POST /api/routerhook/{event}` | 服务端：验证、落库、转推企微 |
| **推送方**（outbound） | 我们把消息推给别人 | `pushToWecom()` → 企业微信群机器人 Webhook | 客户端：构造载荷、发起 POST、判定结果 |

可靠性的责任分割是关键：

- **作为接收方**：可靠性主要由**上游发送方**的重试保证；我们的责任是「**快速 ACK + 幂等**」，让重试安全。
- **作为推送方**：可靠性完全由**我们自己**保证；我们的责任是「**重试 + 终态告警 + 可观测**」，让失败不丢、可见。

两件事的优化方向正好相反，不能混为一谈。

## 2. 现状审计（逐条对照源码）

### 2.1 接收方现状

| 维度 | 现状 | 评价 |
| --- | --- | --- |
| 入口 | `/send`、`/api/send`、`/<key>.send`、`/api/routerhook/{event}` | 4 类入口，覆盖广 |
| 鉴权 | `SEND_TOKEN` 或 KV 轮换密钥（`timingSafeEqual` 常量时间比较），支持 Header / body / query | ✅ 比裸 token 强；❌ **无任何请求级签名**，且 query 传 key 会进日志 |
| 抗重放 | 无时间戳、无 nonce、无事件 ID | ❌ 抓到一次合法请求可无限重放 |
| 幂等 | 无。`saveMessage()` 每次 `generateId()` 新建消息 | ❌ 上游重试 = 重复通知 + 重复企微推送 |
| 请求校验 | RouterHook 严格 JSON 解析（非法 JSON 400）；普通入口 `parseBody` 吞解析错误返回 `{}`；标题 200 / 正文 20000 字符截断 | ⚠️ 普通入口错误语义弱；无整体 body 大小上限 |
| 限流 | 仅 `/api/login` 有失败 8 次锁 5 分钟；**webhook 入口无限流** | ❌ 可被灌爆 KV 写入额度（免费版 1000 次/天） |
| 响应延迟 | `createMessage()` / `serverchanSend()` **await `pushToWecom()` 后才返回** | ⚠️ 企微慢（最多 8s）会拖慢 ACK，可能触发上游超时重试 → 放大重复问题 |
| RouterHook 特例 | 传感器事件走 Durable Object **60s 固定窗口聚合**，同种 `event+unit` 只留最新；Alarm 失败会回写状态、下一窗口重试 | ✅ 这是项目里已有的「**聚合式幂等 + 自重试**」雏形，值得推广到其他入口 |
| 日志/观测 | `console.warn/error`（Turnstile、DO Alarm、未捕获异常）；`/api/status` 有配置自检 | ⚠️ 无投递记录、无成功率、无关联 ID；`pushToWecom` 失败**连日志都没打** |

### 2.2 推送方现状

| 维度 | 现状 | 评价 |
| --- | --- | --- |
| 目标 | 仅企业微信群机器人（`WECOM_WEBHOOK`） | 单点，无备选通道 |
| 协议 | `POST` JSON，8s `AbortSignal.timeout`，检查 `errcode === 0` | ✅ 有超时、有结果判定 |
| 重试 | **无**，单次尝试即结束 | ❌ 网络抖动 / 企微 20 条/分钟限流 → 消息直接丢 |
| 签名 | 不签名（企微机器人本身不要求） | 对现有目标 OK；未来接要求签名的目标时需扩展 |
| 失败处理 | 返回 `{configured, ok, error}`，best-effort 不影响落库 | ⚠️ 设计意图正确（不让下游拖垮主流程），但**没有任何告警**，错误结果默默返回后被丢弃 |
| 可观测 | 无持久化投递记录、无失败计数、无最后成功时间 | ❌ 出问题只能靠人肉翻日志 |

### 2.3 五维度现状评分

| 维度 | 接收方 | 推送方 | 最迫切的缺口 |
| --- | --- | --- | --- |
| 签名校验 | 弱（静态 key，无请求签名） | 不适用（企微不要求） | 入站 HMAC 可选开启 |
| 重试 | 依赖上游，但自身不幂等 | **无重试** | 出站退避重试 + 入站幂等 |
| 幂等 | RouterHook 有雏形，其余无 | 不适用 | 事件 ID 去重 |
| 失败告警 | 不适用 | **完全静默** | 出站失败自通知（P0） |
| 可观测性 | 仅配置自检 | **几乎为零** | 投递记录 + 状态指标（P0） |

## 3. 接收方（别人推给我）：方式矩阵

### 3.1 一览

| 方式 | 适用场景 | 可靠性 | 安全性 | 运维成本 | 对本项目 |
| --- | --- | --- | --- | --- | --- |
| **① 静态 Token / URL key**（现状） | 只能填 URL 的软件、脚本、CI、快捷指令 | 中（依赖上游重试） | 中（query 泄露风险） | 极低 | ✅ 保留，是兼容基石 |
| **② HMAC-SHA256 请求签名** | GitHub/GitLab/Stripe 等平台 webhook、自动化脚本、对防篡改有要求的场景 | 中（本身不管送达） | **高** | 中 | ⭐ **建议补（P1）**，可选开启 |
| **③ 事件 ID 幂等去重** | 所有带重试的上游 | **高** | 中（辅助） | 中 | ⭐ **建议补（P1）** |
| **④ 时间戳 + nonce 防重放** | 与②捆绑，防「抓包后重放」 | 中 | 高 | 中 | ⭐ 随②一起补（5 分钟窗口） |
| **⑤ IP 白名单** | 有固定出口 IP 的平台（少数） | 低（IP 会漂移） | 中（仅纵深防御） | 中高 | ❌ 不作主鉴权，最多辅助 |
| **⑥ 非对称签名（JWT / JWKS）** | 多消费者、密钥不能共享的 SaaS 平台 | 中 | 高 | 高 | ❌ 单用户自研用不上 |
| **⑦ mTLS 双向证书** | 金融/支付机构间私网回调 | 高 | 极高 | 极高 | ❌ Workers 入站场景不匹配 |

### 3.2 方式①：静态 Token / URL key（现状）

- **怎么做**：`?token=<轮换密钥>`、`X-Token` 头，或 `/<key>.send` 路径 key。
- **优点**：任何能发 HTTP 的东西都能用；无需签名库；`timingSafeEqual` 防时序攻击；轮换密钥可一键作废。
- **缺点**：
  - 密钥出现在 URL 时会被浏览器历史、代理日志、聊天截图记录；
  - **无法区分调用方**——所有持有 key 的人权限完全相同；
  - 无时间戳，抓到一条合法请求可以原样重放。
- **可靠性**：完全依赖发送方；我方每次都新建消息，重投即重复。
- **运维成本**：极低，本项目的最大优势，**必须保留**。
- **判断**：✅ 保留为主路径。改进方向是把「header/body 传 key」设为推荐、URL 传 key 标为兼容（README 已这么做），并把签名作为**可选增强**而非替代。

### 3.3 方式②：HMAC-SHA256 请求签名（建议补，P1）

- **原理**：发送方用只有双方知道的 secret，对「时间戳 + 原始 body」算 HMAC-SHA256，放进请求头（如 `X-Notify-Signature: t=<unix>,v1=<hex>`）；接收方用同一 secret 重算，做**常量时间比较**，并检查时间戳在 ±5 分钟内。
- **为什么适合本项目**：
  - Cloudflare Workers 里 `await request.text()` 拿到的就是**未经重新序列化的 raw body**——传统框架最容易踩的「解析后重序列化导致验签失败」坑在这里天然不存在；
  - 项目已有 `hmacHex()` 和 `timingSafeEqual()`（会话 Cookie 在用），可直接复用；
  - 可照 Turnstile 的模式做成「**配置 `WEBHOOK_SIGNING_SECRET` 才开启，不配就完全不影响现有部署**」。
- **优点**：证明请求确实来自持有 secret 的一方、body 未被篡改；secret 不上线不进 URL；配合时间戳可挡重放。
- **缺点**：调用方要会算签名（很多老旧软件做不到）；需要管理 secret 轮换（建议支持双 secret 并行一段时间）。
- **可靠性**：签名本身不保证送达，必须与③幂等配合。
- **安全性**：高。注意三条铁律：**验签在解析 body 之前**、**用 raw body**、**常量时间比较**。
- **运维成本**：中。
- **判断**：⭐ **P1**。建议新增独立端点（如 `POST /api/webhook/{name}`）承载签名模式，现有 `/send` 与 `/<key>.send` 保持零改动，避免破坏兼容。

### 3.4 方式③+④：事件 ID 幂等与时间戳窗口（建议补，P1）

- **做法**：上游每条投递带唯一 `X-Event-ID`（或 `X-GitHub-Delivery` 这类投递 ID），我方把已处理 ID 存起来（TTL 大于上游最大重试窗口，通常 3 天）；重复 ID 直接返回 `200` 但**不落库、不推企微**。
- **关键约束——免费 KV 写额度**：本项目免费版 KV 每天只有 1000 次写，当前每发一条消息已用 2 次写（消息 + 版本号）。若每个事件再单独写一条 dedupe key，额度会迅速吃紧。
- **更省的两种实现**：
  1. **确定性 KV key**：把消息 key 从「时间戳 + 随机 ID」改成含事件 ID 的哈希，`PUT` 同 key 即天然覆盖，只多一次 `get` 判断，不多写；
  2. **复用现有 Durable Object**：DO 的 SQLite 存储有独立额度，且项目已有 `RouterHookSensorDO` 的「相同事件只留最新 + Alarm 重试」范式，扩展一个通用去重 DO 比堆 KV key 更稳。
- **可靠性**：高——这是让「上游重试」从刷屏变成安全网的关键。
- **安全性**：中（主要防重复副作用，不防伪造，需与②配合）。
- **判断**：⭐ **P1**，优先级与②并列；若只能先做一个，**先做幂等**（因为标准重试机制一定会触发重复，而签名缺省关闭）。

### 3.5 方式⑤⑥⑦：不推荐作为现阶段重点

- **IP 白名单**：出口 IP 会漂移、云 IP 会被回收复用，只能当纵深防御的粗过滤，**绝不能替代签名/密钥**；Workers 里还要处理 `CF-Connecting-IP` 的可信链问题。→ ❌ 不做主鉴权。
- **JWT/JWKS**：为「一个发送方广播给多个不可信接收方」设计，本项目是单用户自有服务，共享密钥完全够用。→ ❌ 不做。
- **mTLS**：证书体系运维成本极高，且 Workers 入站 TLS 客户端证书校验不是常规能力。→ ❌ 不做。

## 4. 推送方（我推给别人）：方式矩阵

### 4.1 一览

| 方式 | 适用场景 | 可靠性 | 安全性 | 运维成本 | 对本项目 |
| --- | --- | --- | --- | --- | --- |
| **① 同步 POST 直推**（现状） | 低价值通知、调试 | 低（单次尝试） | 中 | 极低 | ✅ 保留为默认 |
| **② 快速 ACK + 异步投递**（`ctx.waitUntil`） | 所有入站触发的推送 | 中（解耦延迟） | 中 | 低 | ⭐ **建议补（P0/P1）** |
| **③ 指数退避重试 + 死信处理** | 限流、网络抖动、目标临时宕机 | **高** | 中 | 中高 | ⭐ 建议补简化版（P1） |
| **④ 出站请求签名** | 目标是要求签名的自建服务/第三方 | 中 | 高 | 中 | ⏸ 有需求再做（P2） |
| **⑤ 失败告警（自通知）** | 任何推送失败 | — | — | **极低** | ⭐⭐ **最先补（P0）** |
| **⑥ 多目标 + 备用通道** | 企微故障时需要兜底 | 高 | 中 | 中 | ⏸ 视需求（P2） |
| **⑦ 投递记录 / 指标 / 日志** | 排障、SLA 观察 | — | — | 低 | ⭐ **建议补（P0）** |

### 4.2 方式①：同步 POST 直推（现状）

- **优点**：实现最简单，调用方当场拿到 `wecom.ok` 结果。
- **缺点**：`await pushToWecom()` 阻塞响应，企微慢/超时（8s）会拖慢入站 ACK；上游可能超时重投 → 与我方无幂等叠加成重复通知。
- **判断**：✅ 保留语义，但建议按②解耦。

### 4.3 方式②：快速 ACK + 异步投递（建议补，P0/P1）

- **做法**：Worker 的 fetch 签名加 `ctx`，消息**先落库**再立即 `200`，推送放进 `ctx.waitUntil(pushToWecom(...))`。
- **收益**：ACK 从「等企微 8s」降到「等 KV 写入」，从根上减少上游超时重试。
- **代价**：响应体里的 `wecom` 字段不能再是同步结果（可返回 `{ queued: true }`，结果改从投递记录读）。**这是兼容性权衡，需要评估现有调用方是否依赖 `wecom.ok`**——当前 README 把它当调试信息，改起来风险可控。
- **可靠性**：中——请求生命周期内 `waitUntil` 仍会执行，但 Worker 平台不保证无限重试。
- **判断**：⭐ **P0/P1**，与幂等配套收益最大。

### 4.4 方式③：指数退避重试 + 死信处理（建议补简化版，P1）

- **标准做法**：失败后按 1s → 2s → 4s → 8s… 加随机抖动重试，超过上限（通常 ~24h）进死信队列并告警；企业微信群机器人有约 **20 条/分钟**的频率限制，遇 `errcode` 限流尤其需要退避。
- **本项目的轻量实现**：不必上 Cloudflare Queues。可复用已有 DO 的 Alarm 能力——把失败的投递写进 DO 状态，设 Alarm 到期重投，失败则回写 + 再设 Alarm（**现有 `RouterHookSensorDO.alarm()` 已经是这个范式**），超过 N 次则写「死信消息」到通知中心并触发⑤告警。
- **可靠性**：高；**运维成本**：中高（要管重试次数、去重、告警）。
- **判断**：⭐ **P1**，但**必须在⑤失败告警和⑦投递记录之后做**——否则重试本身也不可观测。

### 4.5 方式⑤：失败告警（最先补，P0）

- **现状问题**：`pushToWecom()` 失败只返回一个 error 对象，调用方拿到后并不处理；没有日志、没有告警。消息"落库成功"给人的错觉是已经送达，实际群里什么都没有。
- **最小实现**：
  1. `pushToWecom` 失败时 `console.warn('[notify] wecom push failed:', sanitizedError)`；
  2. 写一条特殊来源（`source: 'system/alert'`）的消息到通知中心，标题如「⚠️ 企微推送失败 N 次」；
  3. 若配置了备用 Webhook，走备用通道告警；连续失败时抑制风暴（如 10 分钟内只告一次）。
- **注意脱敏**：错误里不能带完整 Webhook URL（含 key）。
- **可靠性/运维**：实现成本极低，价值最高。⭐⭐ **P0，第一个做**。

### 4.6 方式⑦：投递记录与可观测性（建议补，P0）

- **最小实现**：
  - 用一个 KV key（如 `meta:delivery:recent`）存最近 20~50 条投递摘要：`{ts, target: 'wecom', ok, retries, errorCode}`，单 key 覆盖写（只 1 次写/投递，可控）；
  - `/api/status` 的 `diagnostics` 增加：`lastPushOkAt`、`lastPushError`、`recentFailures`、`lastEventId`；
  - 日志改成结构化 JSON（`console.warn(JSON.stringify({evt:'wecom.push.fail', code, ms}))`），便于 CF Logs 过滤。
- **判断**：⭐ **P0**，与⑤一起做——没有可观测性，重试和告警效果都无法验证。

### 4.7 方式④⑥：出站签名与多目标（P2，按需求）

- **出站签名**：仅当未来支持「自定义 Webhook 目标」且对方要求签名时才需要；HMAC 逻辑与入站共用。
- **多目标**：可扩展 `targets: [{type:'wecom'|'dingtalk'|'feishu'|'slack'|'telegram'|'custom', url, secret}]`，统一投递框架；这是"更多推送方式"的产品化方向，但属于**功能扩展**而非可靠性补齐，排序靠后。

## 5. 五个重点维度的落地设计

### 5.1 签名校验（入站）

```
发送方:  signature = HMAC_SHA256(secret, "<unix_ts>.<raw_body>")
         header: X-Notify-Signature: t=<unix>,v1=<hex>
接收方:  1. 取 raw body（request.text()，务必在 JSON.parse 之前）
         2. 解析 header 的 t / v1，检查 |now - t| <= 300s
         3. 用同一 secret 重算 HMAC，timingSafeEqual 常量时间比较
         4. 任一失败 → 400，响应体不透露是"签名错"还是"时间戳过期"
         5. 通过后再解析 JSON、做幂等判断、落库
```

- 项目已有 `hmacHex()` + `timingSafeEqual()`，可直接复用；
- secret 放 Cloudflare Secret，**支持新旧两个同时有效**以便无损轮换；
- **默认关闭**，配置才启用——与 Turnstile 的一致体验。

### 5.2 重试

- **入站**：不自己重试；做到「先持久化再 2xx」「幂等」「 ACK 快」三件事，让上游重试变得安全。
- **出站**：简化版指数退避（1/4/16s，3 次），失败记录进投递日志；终态失败走死信消息 + 告警。
- 重试请求必须带**同一个事件 ID**，否则幂等失效。

### 5.3 幂等

- 事件 ID 由发送方生成（UUID 或平台投递 ID）；接收方以 `(source, eventId)` 为键。
- 优先用**确定性 KV key** 或**复用 DO** 避免额外 KV 写入（免费额度约束见 §3.4）。
- dedupe 记录的 TTL ≥ 上游最大重试窗口（常见 3 天）。
- DO 聚合已证明这条路可行：把「相同 event+unit 只留最新 + Alarm 到期推一次」泛化即可。

### 5.4 失败告警

- 失败即结构化日志 + 计数；连续失败达阈值（如 3 次）或 10 分钟内重复失败，发一条系统告警消息；
- 告警本身也要防环：告警消息不再触发告警（用 `source: 'system/alert'` 标记短路）；
- 错误脱敏：不回显 Webhook URL、secret、完整响应体。

### 5.5 可观测性

- 三个层次：**日志**（结构化事件）、**状态**（`/api/status` 的投递指标）、**历史**（最近投递记录可查）。
- 关联 ID：每条消息生成 `eventId`，贯穿入站接收 → 落库 → 出站投递 → 告警，排障时可串起来。
- 指标关注：投递成功率、平均/最大延迟、重试次数分布、失败原因分类、最近成功时间。

## 6. 优先级路线图

| 阶段 | 动作 | 收益 | 兼容风险 |
| --- | --- | --- | --- |
| **P0-a** | 出站失败 `console.warn` + 失败告警消息（防环、脱敏） | 失败不再静默 | 无 |
| **P0-b** | 最近投递记录（单 KV key 环形缓冲）+ `/api/status` 指标 | 排障从翻日志变成看页面 | 无 |
| **P1-a** | 事件 ID 幂等（确定性 key 或复用 DO） | 上游重试不再刷屏 | 低（对无 eventId 的请求走原逻辑） |
| **P1-b** | `ctx.waitUntil` 异步投递 | ACK 更快，减少超时重试 | 中（`wecom` 字段语义变化，需告知） |
| **P1-c** | 可选 HMAC 签名端点（新路径，默认关） | 防伪造/篡改，可接正规平台 webhook | 无（新端点，旧端点不动） |
| **P2-a** | 出站退避重试（复用 DO Alarm）+ 死信 | 限流/抖动不丢消息 | 中 |
| **P2-b** | 出站签名 + 多目标（企微/钉钉/飞书/Slack/自定义） | 产品化扩展 | 中 |

> 每个阶段都要跑现有 9 套回归测试；改 `UI_HTML` / `LOGIN_HTML` 模板字面量必须跑 `_test_render_syntax.mjs` 与 `_test_render_dom.mjs`（历史踩坑，见 `TROUBLESHOOTING.md`）。部署时 `--keep-vars`，代码更新后**同步创建 Release**（见 `COMMERCIAL_LICENSE.md` 所在仓库的发布流程）。

## 7. 明确不建议补的方案

| 方案 | 不建议的原因 |
| --- | --- |
| mTLS 双向证书 | Workers 入站客户端证书校验不常规；证书签发/轮换运维成本远超本项目收益 |
| JWT / JWKS 非对称验签 | 为多消费者、不可共享密钥的 SaaS 设计；单用户自有服务用共享 HMAC 足够 |
| IP 白名单作主鉴权 | IP 漂移与云 IP 复用会误伤，且不能防持有合法 key 的攻击者；仅可作辅助 |
| 独立队列 + DLQ 重型架构 | Cloudflare Queues 有成本与配置复杂度；现有 DO Alarm 已能承载简化版重试 |
| 出站"恰好一次"承诺 | 分布式系统上不成立；正确目标是「至少一次 + 幂等」，不要过度承诺 |
| 收到请求就回 200 但丢弃消息 | 违反「先持久化再 ACK」，会静默丢数据 |

## 8. 一句话判断

> 本项目的核心竞争力是「**极简 + 免费 + 自研**」，不要为可靠性引入重型架构。按 **P0 失败告警与可观测 → P1 幂等与可选签名 → P2 重试与多目标** 的顺序推进，每一阶段都保持「不配置就完全不影响现有部署」，才不会把一个好用的一文件工具变成需要运维的系统。
